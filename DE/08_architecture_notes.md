# Architecture and implementation notes

Streamlit renders the existing simulator and prediction paths. After its cached model call returns, Live Monitor offers the episode to PostgreSQL in a separate transaction. The episode key gates three batched inserts for readings, predictions and factors. PostgreSQL serializes conflicts on the unique key, so concurrent initial saves leave one complete episode. Stub results stay out of the model tables.

The existing alert code still decides when to send and uses the same Telegram destination. The database stores the effective alert level, links the raw prediction when context is available, and copies the returned Telegram status to active-recipient junction rows. Those rows represent the shared send outcome, and no per-recipient routing or delivery confirmation occurs. Missing connection settings or a failed initial connection activate the SQLite alert log. During an outage, the two logs can diverge and require an explicit migration.

The app uses short-lived connections with a five-second connection timeout. Referential constraints, transaction rollback, batch operations and conflict handling preserve consistency. See [schema and indexes](04_schema.md). Published observations are seeded separately from synthetic readings, and Lake Growth uses the published CSV when PostgreSQL reads are unavailable.

As volume grows, measure index selectivity and query plans with `EXPLAIN (ANALYZE, BUFFERS)` in a test database. Pool connections when concurrent sessions make connection setup measurable. Exact table counts can become expensive, so a future operational view could use estimated counts. For large continuous sensor streams, consider monthly timestamp partitions or TimescaleDB hypertables. A partition key must be included in partitioned unique keys, so the existing episode-hour uniqueness and prediction foreign key would need a deliberate redesign first. A future retention policy should keep published observations and warning history according to project needs, while expiring older synthetic episodes and their prediction rows.

Stored predictions make future dashboard history reads possible without recomputing model scores. Live Monitor currently keeps its existing cached model-first behavior. Cold cache inference runs once per reading, playback intentionally sleeps and redraws growing charts, and alert persistence currently scans a prefix of predicted levels per displayed frame. These bottlenecks were observed in the code. No timings are implied.
